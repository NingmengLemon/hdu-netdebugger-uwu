## 还没做的新能力

按证据强度排序：

1. **Wi-Fi 状态**：SSID / 信号 / 频段。手册给出至少 `i-HDU` 与 `eduroam` 两个 SSID；
   实现要注意 `netsh` 输出是 OEM 编码（`net/console.py` 已经有解码先例），
   而且无线开放情况本身一直在变、只有无线接入时才有数据。
2. **IPv6 那一路的验证**：检查 38 的"没有可用 v6 地址"分支已在真机验证（本机只有链路
   本地 + Teredo），但**"有 v6 地址"的正向分支在本网无法验证** —— 本机既没有全局 IPv6，
   也没有校园 v6 出口。等到能连 v6 的环境再跑一遍。
3. **教学区 / Linux 的实机覆盖**：现有验证都在同一台 Windows 机器上做的。教学区的
   BAS / 认证测试点、Linux 上的系统 ping 解析与 `ping -M do`（路径 MTU 用）都还等着
   真机跑一遍 —— 这类"换平台就走的另一条代码路径"最容易藏问题。

## 已知的机制疑点

工具只能给出边界，改不了中间设备；下面这些是**证据已足但结论未闭环**的：

1. **深澜 `192.168.112.97` 为什么在 996 字节以上静默丢包（≈ MTU 1024）**：
   是那台主机 / 前置设备丢大包，还是路径 MTU 真的只有 1024？控制变量已排除
   "DF 标志被丢"（DF + 32 字节 2/2 通）。
2. **阿里 DNS 的 DF 上限为什么是 1456（≈ 1484）**而不是 1472 / 1492：疑似隧道或运营商
   策略，缺机制证据。
3. **校园 DNS 的分域解析与"本机 DNS 被接管"如何共存**：手册说校内域名由应用网关
   交校内 DNS 解析，而工具检测的是"向不可路由地址查询也能得到答案"（本地拦截）。
   有自建 DNS 时两者都成立，判据需要更细。
4. **教学区与生活区是否同一套认证 / 网关**：手册暗示不同（`192.168.112.30` vs `.97`、
   `login.hdu.edu.cn`）。
5. **"掉学校认证"与"代拨掉线"如何区分**：管理员说校园网与寝室宽带是两套系统，
   工具目前看不出来。
6. **ICMPv6 Type 2 缺失的责任段**：群反馈的结论是"上游设备缺陷"，未闭环。
